# 给 AI Agent 写了个浏览器，实测比 Chrome 快 7.6 倍、内存只有十分之一

先说结论：我们做了个专门给 AI Agent 用的浏览器 aginxbrowser（Rust 写的，Apache-2.0 开源，MCP 原生）。8 月 28 号在本机跑了一轮基准，20 个真实网页、双轮、对照无头 Chrome `--dump-dom`：

- 耗时中位数：我们 532ms，Chrome 4053ms，差 7.6 倍
- 内存：我们单进程全程峰值 227MB；Chrome 每开一个页，进程树加起来约 2.1GB
- 可靠性：Chrome 有 5/40 次返回 0 字节的 DOM（python.org 两轮全挂，react.dev、bun.sh、vitejs.dev 偶发挂），我们 0 失败

机器是 Apple Silicon macOS，网络是国内普通出口。测试脚本就在仓库 `bench/` 目录里，`python3 bench/run.py` 可以原样复现。

## 为什么要单独造一个？Chrome 不是有 headless 吗

因为 Chrome 是给人眼设计的，Agent 要的东西它一点都不在乎。

一个网页渲染给人看，需要 GPU 合成、动画帧、字体抗锯齿、图片解码、排版引擎跑全套。这些吃掉的就是那 2.1GB 和 4 秒钟。但 Agent 抓一个页面，要的是什么？DOM 结构、文本内容、JS 执行完之后的状态。它不看像素。

所以市面上给 Agent 接浏览器的方案（Playwright、Puppeteer、CDP 直连）本质都是"牵着一头大象去捡芝麻"：为了读一段文本，把整套为人类视觉优化的渲染管线全跑一遍。网页一多，内存先爆；国内网络一抖，Chrome 的加载策略直接给你返回个空 DOM——而且它不报错，静默失败，Agent 拿着空结果继续往下推理，错得理直气壮。

那 5/40 的 0 字节失败，我们复盘过：不是噪声，是 Chrome 加载策略在国内路由下的系统性行为。对自动化场景来说这比慢更可怕——慢你能等，空结果你不一定发现得了。

## 我们的做法：九成页面根本不该起引擎

aginxbrowser 是分层的。一个 URL 进来，先走 Tier 1：纯 HTTP 抓取 + HTML 解析 + 正文提取。实测下来 36/40 的页面到这一层内容就够了，根本不需要执行 JS——那 532ms 里大头其实就是网络往返。

只有当页面真的是 JS 渲染的（内容启发式判断正文不够），才升到 Tier 2，起我们内置的 JS 引擎把页面真正跑一遍。引擎叫谛听（diting），技术谱系来自开源社区 obscura/blitz 这条线，我们在上面做了大量面向 Agent 场景的改造：stealth TLS 指纹、有状态 session、CDP 兼容接口、MCP 工具直接暴露给 Agent。

输出是 Markdown 或结构化提取结果，直接喂给模型，不用 Agent 自己再剥一遍 HTML。

## 踩坑实录：让掘金过掉字节 WAF 的三层洞

光说不练没意思，讲个具体的。掘金（juejin.cn）这种字节系站点有套 WAF JS 挑战：首次访问返回一个 930 字节的挑战页，页面里的脚本做 SHA256 暴力破解（服务器给个前缀和目标哈希，让你枚举一个小数字，实测答案都在 1~200 之间），算出来种进 `_wafchallengeid` cookie 再 reload，才放你看到真页面。

我们的引擎过这个挑战，前前后后修了三个洞，一个比一个隐蔽：

**第一层：`<body onload>` 永远不被触发。** 挑战页是靠 body 标签上的 onload 属性启动整套流程的。我们的引擎按常规理解把 load 事件派发到 window 上，而 load 不冒泡——挂在 body 上的属性 handler 就永远收不到。翻 spec 才发现：body 元素上的 window 类事件属性，本来就等价于 window handler，这是 HTML 标准里很角落的一条。补上属性转发之后，整个流程全自动：onload → PoW 几毫秒算完 → 种 cookie → 24ms 内带着答案 reload。

**第二层：eval 把语句当表达式包。** 挑战脚本里有 `try{}` 这类语句，我们的 evaluate 只认 6 个语句关键字，其余一律包成 `return (...)` 再执行——语句包进括号就是 SyntaxError，而且这个错误还被吞成了 null，表面上"执行成功，什么都没发生"。改成间接 eval（CDP 语义：语句、完成值、全局作用域）才算完。这种"静默吞错"的 bug 最恶心，排查时你以为 WAF 升级了，其实是自己引擎的坑。

**第三层：修完引擎，抓取接口还是返回挑战页。** 这次根因根本不在浏览器——Tier 1 的"内容是否足够"启发式，把挑战页里 inline 脚本的可见文本也算进去了。930 字节里有几百字符的"正文"，启发式一拍脑袋：内容够了，不用起引擎。于是一个专门用来拦住非浏览器访问的页面，被我们自己的快路径当成了正文返回。修法和前两层完全不同：认签名让路，检测到 WAF 挑战特征就强制升级到 Tier 2。

还有个小插曲：挑战过了、页面结构也对了，掘金首页信息流还是空的。查了一圈，页面内 fetch 返回 200 但 data 是 null——拿裸 curl 试，一样 null。是掘金的登录墙，不是引擎的锅。这种"先怀疑别人再怀疑自己"的顺序，是这几个月排查省时间的第一原则。

## 另一个差点劝退的坑：V8 默认栈只有 1MB 不到

掘金的前端 bundle 在我们的引擎里直接抛 `RangeError: Maximum call stack size exceeded`，页面渲染出来一屏报错堆栈。

查到底：V8 的 JS 栈默认上限大约 984KB，跟线程栈多大没关系；而我们的宿主线程自己也只有 2MB。真实前端代码（尤其是打包压缩过的）递归深度轻轻松松破这个数。修法是给 V8 isolate 初始化时设 `--stack-size` 到 32MB，宿主侧换专用深栈线程。回归测试是 20000 帧递归跑真页面，468 个测试全绿。

这件事给我们的教训是：跑合成测试页面和跑真实互联网是两个世界。合成页面永远不会告诉你 V8 默认栈不够、body onload 不冒泡、WAF 挑战页会被当正文。

## 诚实声明

有几点我们自己也还在意，先说出来免得打脸：

- **Token 效率没叙事里那么美。** 我们输出的 Markdown 字符数比 Chrome 剥标签后的纯文本多 2.3 倍——因为 Markdown 把链接 URL 写全了。对模型来说这通常是对的（链接是信息），但你要纯省 token，记得用 `max_chars` 或者 `selector` 参数裁一裁。
- **登录墙还是墙。** 要登录才能看的内容，引擎再强也没用，得给 cookie。
- **基准是国内网络 + 20 个页面。** 换一批页面、换一个网络，数字会变。脚本开源，欢迎跑出不同的数字来打我们脸。
