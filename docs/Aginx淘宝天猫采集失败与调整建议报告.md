## 四、失败原因判断

### 1. 淘宝重新对 Aginx 会话进行风控判断

人工浏览器里没有滑块，只能说明人工浏览器的那套会话通过了验证。复制 Cookie 到 Aginx 后，淘宝会在新的浏览器上下文中重新检查风险。Cookie 本身不能完整携带：

- localStorage 和 sessionStorage；
- 设备指纹和硬件种子；
- TLS 指纹和浏览器环境特征；
- 已完成滑块验证后产生的临时上下文。

所以“人工页面没有滑块”和“Aginx 页面没有滑块”不是同一个条件。

### 2. 之前退出登录使旧验证上下文失效

第一次注入后用户退出了淘宝登录。之后的 cURL 虽然仍能导入 Cookie，但淘宝已经把它视为新的会话，原先短时效令牌和验证状态不能稳定复用。

### 3. User-Agent 和 TLS 指纹存在差异

用户复制的人工请求使用 Chrome 153，而 Aginx 默认使用 Chrome 145/TLS Chrome 145。测试中把会话 User-Agent 对齐到 Chrome 145 后仍然触发滑块，说明这不是唯一原因，但它会增加风险分数，不能忽略。

### 4. Aginx 当前不能自动完成淘宝滑块

本机能力显示 `captcha_solver=false`。Aginx 能检测到淘宝的 x5 风控墙，但不能自动取得淘宝要求的滑块验证结果。

### 5. 本地滑块渲染异常

在 Aginx 页面状态中，滑块手柄可定位，但轨道宽度为 0。此前尝试拖动后淘宝返回验证错误，说明拖动没有产生淘宝认可的有效轨迹。继续盲目重复拖动只会增加风控风险。

## 五、为什么上周可以、现在不行

这不是用户操作错误，也不是 cURL 格式突然失效。淘宝的风险控制会随账号、IP、设备指纹、请求频率、Cookie 时效和页面风控策略变化。上周第一次会话曾短暂读到真实数据，说明当时风险评分较低或验证状态仍有效；之后退出登录、重复导入和多次访问使新的 Aginx 会话被重新评估，最终进入滑块风控。

此外，目标页面当前使用的天猫详情页和风控资源也可能已经更新。相同商品链接并不保证每次请求都返回相同的页面状态。

## 六、需要调整的内容

### 用户侧只需要保持的条件

1. 人工环境保持淘宝登录，不要在采集过程中退出。
2. 页面已经显示商品标题、图片、SKU 和价格后，不要连续刷新。
3. 如需重新提供请求，优先复制 Network 中实际成功的 `mtop`/`api`/`detail`/`sku` 请求，而不是只复制地址栏的 Document 请求。
4. cURL 复制后立即交给 Aginx 导入，避免等待令牌过期。

### Aginx 侧需要解决的条件

1. 在同一个 Aginx 会话中完成人工验证和后续采集，不能只把 Cookie 当作完整登录状态。
2. 修复本地滑块轨道宽度为 0 的渲染问题，或提供可用的 Aginx 人工接管页面。
3. 保持 User-Agent、TLS 指纹、代理出口和会话状态一致。
4. 验证失败后停止重复重试，等待风控冷却后再建立一次新会话。

## 七、推荐的继续方案

当前最合理的顺序是：

1. 先解决本地 Aginx 的人工接管/滑块渲染问题。
2. 在同一 Aginx 会话中完成一次淘宝验证。
3. 验证通过后立即读取页面状态和网络请求。
4. 通过页面脚本提取商品标题、规格、SKU ID、价格和图片 URL。
5. 使用 Aginx 下载接口保存图片，不把验证码占位资源混入商品素材。
6. 生成以下交付文件：

   ```text
   商品信息.md
   SKU清单.csv
   主图/
   详情图/
   SKU图/
   ```

如果暂时无法提供同一会话内的人工接管，继续重复复制 Cookie 或重复拖动滑块预计不会产生新的有效结果。

## 八、采集完成的验收标准

本次采集只有同时满足以下条件，才算完成：

- 页面标题不是“验证码拦截”；
- Aginx 挑战检测结果为无风控事件；
- 页面正文包含商品标题、规格或价格字段；
- 图片 URL 不再是 `XXXXX` 等验证码占位资源；
- SKU 清单至少包含规格名称、SKU ID 和对应价格；
- SKU 图片与 SKU 名称能够一一对应；
- 原始素材、解析结果和后续优化素材分别保存。
