## 四、具体卡点、原因、如何处理

### 1. 店铺/账号确认太晚，前期做了无效准备

**现象：** 用户此前使用过不同买家及卖家账号。早期流程拿到可用登录态，不代表它就是本次目标店铺；26 张图曾先上传到非目标账号素材空间。

**责任判断：** 这是我们流程前置检查不足，不能称作 Aginx 登录功能本身失效。单纯“有 Cookie”“不是登录页”都不足以确认卖家身份。

**本次处理：** 明确目标为婧途车品旗舰店后，建立独立卖家 cookie store 和店铺专属素材映射；提交前检查当前页面卖家身份，成功后又以公开商品页店铺名复核。

**建议：** 我们必须在传第一张图前锁定商店；Aginx 可提供具名隔离 profile/context 和脱敏身份摘要，标明 buyer/seller、目标域及授权状态。账号不匹配时停止写操作。不要依赖顶部导航的买家昵称判断天猫商家身份。

### 2. 页面看起来加载了，但发布引擎尚未可用

**现象：** 曾出现 `pageState: undefined`、提交方法不存在；恢复页面生命周期后才出现 `pageState: object`、`submit: function`。前期日志还记录 React #327；只读诊断的一次站点请求包装器测试记录 React #200。

**原因边界：** 证明了页面应用初始化/渲染链路在这些会话里不完整，但**不能仅凭 React 压缩错误号确定是 Aginx 某一个 DOM API 的缺陷**。我们的过早初始化和补丁顺序也可能放大问题。尤其 #200 来自把 HTML 返回交给站点请求包装器的诊断，不足以证明一般 GET/XHR 失效；普通 Fetch/XHR 的同页 GET 都成功 200。

**本次处理：** 使用页面本身生命周期恢复、等待初始化、fresh session 重新做预检。最终成功会话中 core store 已存在，不再把缺失状态简单当成“可以立刻重提”。

**建议：** Aginx 提供应用级 `waitForFunction`/条件等待、生命周期事件日志、DOM 挂载节点和任务调度信息；我们的适配器把“页面加载”和“表单就绪”分开。不要用一个固定 sleep 或 `readyState=complete` 代替真实就绪检查。

### 3. 类目上下文被模型更新过程破坏

**证据：** 服务端返回 `PUB_BIZCHECK_CAT_ID_NOTEXIST`，消息“类目为空或不存在，请重新选择类目后尝试发品”。页面入口本身已经带 `catId=201305805`。

**定位：** 本次排查发现，适配器更新模型/错误消息时，没有可靠保留 `global.catId` 等完整上下文。对页面模型 API 的增量更新语义使用不稳妥。

**本次处理：** 恢复完整 `Json.models`，使用原生模型 API 的合并参数，局部更新不再丢掉全局类目和商品上下文；提交前同时检查外层 `catId`、商品上下文及内层表单。

**责任判断：** 优先归为我们的天猫适配器问题，不应要求 Aginx 无差别改变所有网站的 `updateModels` 语义。后续应采用局部包装/完整模型更新，减少临时全局覆盖。

### 4. 短标题和必需素材未在一开始检查完

两项服务端明确拒绝：

- `shopping_title / CHK_BASIC_LENGTH_LONG_BYTE`：“不能超过15个汉字或30个字符”。
- `guideImageGroup / CHK_BASIC_REQUIRED`：“透明素材图为必填项，不能为空”。

**本次处理：** 短标题改为“26款比亚迪大汉屏幕钢化膜”，完整商品标题保留；用户批准后补充独立裸膜透明 PNG。

**为什么拖慢：** 这些要求是在较晚的服务端校验中逐项暴露。透明图还需要新制作和人工审图；两次生成稿虽然看起来像透明背景，但实际为 RGB/棋盘格像素，必须本地抠图并检验 alpha。

**责任判断：** 短标题、必填素材预检缺失是我们的适配器问题；假透明稿属于图像制作/导出问题，**不是 Aginx 上传失败**。

**建议：** 在素材制作前读取当前类目全部必填项、条件规则、标题长度算法及素材规格，合并列出缺项。透明图在本地及 CDN 两端检验 MIME、尺寸、alpha、透明像素，不凭扩展名和棋盘格外观判断。

### 5. “新品材料证明”条件字段误进入必填校验

**证据：** `FE_ERROR_RICH_IMAGES_REQUIRED`；本次检查点 `clicked:true, called:false`，卡在前端，未进入提交方法。

已读到页面原生规则：未选择新品申报，或所选值不为 1 时，隐藏 `newProductConfirmation`。当时选择值不存在/未开启，却仍执行该字段的必填检查。

**本次处理：** 按服务器提供的原始条件恢复可见性；没有关闭 required、没有虚构证明、没有绕过服务器验证。最终 fresh session 的正常模型预检通过，没有再次依赖该条件恢复脚本。

**原因边界：** 可能涉及生命周期/条件规则调度以及我们的手动恢复过程，尚缺干净 Chromium 对照，不能直接定性为平台规则错误。

**建议：** Aginx 为条件联动提供事件顺序和依赖值观测；适配器优先重新正常初始化，让原生规则运行，不把隐藏字段必填错误一律“清空/跳过”。验收必须覆盖申报关闭和开启两条分支。

### 6. 点过发布，但不知道请求到底有没有完成——最影响体验的卡点

**现象：** 旧脚本点击提交后立即返回，再 sleep/轮询全局变量；曾得到 `[object Object]`、空回执、未 settled 状态。次日读取某个旧会话时，原有诊断对象已经是 `null`。历史检查点还记录同步超时/watchdog 终止，但本报告未取得完整原始调度轨迹。

**为什么必须停：** “没有看到成功响应”不等于“服务器没有创建商品”。再次点击可能重复上架；商品列表恰好又空白，无法自行可靠确认，只能保存检查点并请用户核对。

**本次有效修复：**

1. 用户明确回复“没有”后，关闭旧任务专用会话。
2. 新会话先做只读运行时检查，恢复已上传素材，不重复传图。
3. 新脚本保存长期 Promise；区分 `clicked → nativeSubmitEntered → requestEntered → requestSettled → settled`。
4. dry-run 检查真实原生参数，到达请求边界主动阻止发送。
5. 正式运行同时保护“提交方法只能进入一次”和“原生请求只能进入一次”，等待原生回调；不只等待 click 返回。
6. 成功 URL 出现后，再开成功页、编辑页和前台核验。

**责任判断：** 我们旧脚本没有充分等待和保存完成状态，确有改进责任。最后成功证明本场景并非“Aginx 根本不支持 Promise/Fetch”。同时，Aginx 对任务未完成、超时、上下文失效的返回语义和持久状态不够可观测，放大了排查成本。仅凭本次结果无法证明是单一 Promise bug。

**Aginx 建议：** 提供长任务 operation ID、可查询状态、结构化异常和显式截止时间。区分 `pending / resolved / rejected / timed_out / cancelled / context_destroyed`，另区分正常 `null`、`undefined` 与执行未结束。上下文销毁前保存最后状态。客户端去重不能替代天猫服务端幂等；结果不确定必须先查证，不能自动重提。

### 7. 简单 eval 每次也要 6～8 秒

以下 6 项在同一个正确卖家发布会话顺序执行。数值是客户端 HTTP 调用墙钟时间，不是 JS 函数自身耗时。

| 只读测试 | 返回结果 | 耗时 |
| --- | --- | ---: |
| 身份与引擎布尔值检查 | 正确店铺、engine/core store 存在 | 6084 ms |
| `Promise.resolve().then(...)` | 成功 | 7507 ms |
| 50ms `setTimeout` Promise | 成功 | 7595 ms |
| 原生 Fetch 同页 GET | 200 | 8279 ms |
| 原生 XHR 同页 GET | load / 200 | 8331 ms |
| 站点 request 包装器只读测试 | Promise 结束，React #200 错误 | 8193 ms |
| 合计 / 平均 | 6 次 | 45989 ms / 7664.8 ms |

**能得出的结论：** 很小的读取也有明显延迟，连续多轮调试会放大总耗时。按该样本均值推算，50 次串行调用约 6.4 分钟、100 次约 12.8 分钟；这是说明性估算，**不是本次实际调用次数统计**。

**不能得出的结论：** 不能直接断定存在固定 7.5 秒 sleep，也不能把全部耗时算作 JS 执行或淘宝网络慢。

**建议：** 分别记录排队、执行、Promise 等待、网络空闲等待、序列化、回传耗时。对纯 DOM/同步返回提供无需等待整页网络空闲的模式；结果已 resolved 时是否还等待固定周期，应重点检查。对空白页与本天猫复杂页各跑多轮，给出 p50/p95，而不是只跑一次测速。我们也应合并同阶段只读检查、减少连续小调用和固定 sleep。

### 8. 发布后回读又遇到两类“看起来没保存”的假象

**A. 手机详情 XML 解析：确定可复现的兼容性问题。**

实际存储的手机 XML 有 8 个 `<img>图片地址</img>`；Aginx 的 `DOMParser(..., 'text/xml')` 解析结果把它当 HTML 的 void img，`textContent` 返回空字符串，`outerHTML` 变成 `<img size="...">`。原始 XML 内容并未丢失。

最小只读复现，不需要登录也不需要访问天猫：

```javascript
const xml = '<wapDesc><img size="123">https://example.com/one.jpg</img></wapDesc>';
const doc = new DOMParser().parseFromString(xml, 'text/xml');
const img = doc.querySelector('img');
JSON.stringify({ text: img.textContent, serialized: img.outerHTML });
// 预期 text 为 https://example.com/one.jpg，并保留 XML 元素的文本子节点。
// 本次 Aginx 对真实同形 XML 的观测：text 为空，img 被当作 HTML 空元素。
```

我们的临时修复：针对这份已知格式从原始 XML 提取图片地址；这不是通用 XML 解析器替代方案。Aginx 应按 MIME 区分 HTML/XML，覆盖闭合标签、文本节点、命名空间、CDATA、解析错误等回归测试。

**B. 手机原生详情辅助组件被算作图片：我们核验脚本的问题。**

原生详情有 8 个图片组件，加 2 个辅助/结束组件（其中包含“已经到最底了”），初次用数组总长度误计成 10。改为只统计含图片地址的组件后，8 张顺序全部一致。商品不需要修改。

**C. 前台详情在 Aginx 尚未渲染：未定位的剩余问题。**

前台标题、店铺、13 SKU、5 主图资源、13 SKU 图资源正常；点击“图文详情”后仍未在 DOM 看到 8 张详情图。没有显示验证码。相关详情脚本返回 200，但“脚本 200”并不代表详情业务接口或组件已成功完成。

后台电脑 HTML、手机 XML、手机原生图片组件、新版详情四份数据均完整，不能因此反复覆盖详情或重新发布。需要 Aginx 与普通 Chromium 同商品、同登录态对比，记录详情接口的脱敏业务状态、IntersectionObserver、滚动/懒加载和组件异常。尚未完成普通浏览器对照，不宣称已经证明唯一根因。

## 六、给 Aginx 的优化清单与验收方法

下列是**建议功能/测试目标**，不是声称 Aginx 当前已有这些 API。

| 优先级 | 优化项 | 建议实现与可验收结果 |
| --- | --- | --- |
| P0 | 长任务状态与异常可观测性 | 返回 operation ID；保存关键状态与脱敏异常；连接超时后可查询；区分未完成、正常 null、异常、上下文销毁；成功回执不能因页面跳转丢失 |
| P0 | 正式操作防重复 | 每个客户端 attempt 设置一次性执行锁；结果未知不自动重发；对“回调晚于 HTTP 超时”“页面跳转”“会话关闭”做故障注入测试并可追踪最后已知状态 |
| P0 | 应用就绪判断 | 支持条件等待与显式 timeout，观测 hydration/挂载/事件；在页面可见而 handler 未注册时不能报告就绪；避免用户脚本强行多次触发生命周期 |
| P1 | eval 延迟分解与快速读取 | 响应附分阶段 timings；同步/已 resolved 结果不无条件等待全页 idle；空白页和天猫页各跑至少 30 次基准，输出 p50/p95，解释本次 6～8 秒来源 |
| P1 | XML DOMParser 兼容 | 对上述最小复现正确返回文本；不能将 XML img 按 HTML void 元素处理；补 HTML/XML 分支回归测试 |
| P1 | SPA 商品列表、详情渲染 | 普通 Chromium 与 Aginx 对照；核对 hydration、懒加载、滚动、IntersectionObserver 和详情业务状态；后台已存 8 图时能在正常加载后观察到对应详情内容 |
| P1 | 买家/卖家和店铺隔离 | 使用独立命名 profile/context；提供无凭据的身份摘要、会话失效原因；切换账号不串 Cookie、LocalStorage 或素材空间 |
| P2 | 原生文件上传通道 | 本地文件/流式 Blob handle、进度、文件级错误与断点；避免由脚本将全部 base64 放入 eval。复用已上传素材必须同时校验店铺归属和文件哈希 |
| P2 | 诊断导出包 | 一键导出脱敏版本信息、阶段耗时、错误栈、方法/域名/路径/状态及关联 operation ID；默认移除 Cookie、授权头、签名、临时查询参数 |

性能验收不应只承诺“整体更快”。先在稳定测试页消除无关等待，再在本天猫页面重复测量；把网络等待与 Aginx 自身等待分开，以可复现数据说明改进。

## 七、我们自己的自动化也必须改

1. 上传第一张图之前确认目标店铺，买家参考会话与卖家发布会话严格分离。
2. 按平台和类目使用独立适配器；旧淘宝草稿不能直接喂给天猫。避免旧品牌、颜色枚举和运费模板混入新店。
3. 素材开始制作前一次性列出 5 主图、详情、SKU、必需导购图等缺项；按真实字段规则验证短标题。
4. 提交前保留完整模型和业务上下文，优先调用原生验证；dry-run 与正式发布使用同一参数检查逻辑。
5. 正式提交必须等待原生结果并保存状态，不能把 click 完成当作发布完成，也不能把空返回当成失败后立刻重试。
6. 每次动作写追加式事件日志：开始、请求进入、返回、错误、人工等待开始/结束。不要反复覆盖同一 JSON 导致历史耗时丢失。
7. 合并可并行/可批量的只读查询，减少固定等待；发布动作本身保持串行一次性。
8. 核验器区分“资源已保存”“页面已渲染”“图片已加载”；按组件类型统计图片，允许平台换 CDN 地址后用内容验证。
